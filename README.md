# Quality Dashboard

Generated by the BRD Architect platform. The specification lives in `spec/`; approved reference documents (the solution design this build follows) are in `docs/`.

Pushes to `main` trigger an automatic redeploy.

## What this app is

Quality Dashboard is a serverless AWS pipeline that pulls software-quality
signal from five separate tools (SonarQube, GitLab, Fortify SSC, Trivy,
Tricentis Tosca), normalizes each tool's shape into one shared relational
model, and evaluates it against per-project release-gate thresholds. It is
built as an AWS SAM application: every AWS resource lives in `template.yaml`.

The full pipeline described in `spec/tasks.md` is implemented and tested:
ingest (pulling raw tool data and landing it in S3), normalize (turning it
into rows in `metrics`, `findings`, `finding_lifecycle_events`, and
`ingestion_batches`), nightly gate evaluation against per-project
thresholds, Slack/email breach notifications, the read/write dashboard API,
and a React SPA frontend. See the sections below for each slice, and
"Deployment" at the end for how `./deploy.sh`/`./destroy.sh` wire it all
together.

## Ingest -> S3 envelope -> SQS -> normalize flow

1. **Ingest.** Two ingest styles exist, one Lambda per tool:
   - *API pull* (`src/handlers/ingest-api-sonarqube.js`,
     `ingest-api-gitlab.js`, backed by `src/ingest/apiPull.js`): loads the
     tool's Secrets Manager secret, calls the tool's REST API per configured
     project (`src/ingest/sources/sonarqube.js`, `sources/gitlab.js`).
   - *SFTP pull* (`ingest-sftp-fortify.js`, `ingest-sftp-trivy.js`,
     `ingest-sftp-tricentis.js`, backed by `src/ingest/sftpPull.js`): connects
     over SFTP with a Secrets-Manager-held private key and downloads one file
     per configured project.
   Both styles converge on `src/ingest/publishBatch.js`, which:
   - writes a JSON **envelope** to S3 at
     `raw/{tool}/{project_id}/{run_date}/data.json`:
     ```json
     {
       "envelope_version": 1,
       "tool": "sonarqube",
       "project_id": "checkout-svc",
       "run_date": "2026-09-01",
       "fetched_at": "2026-09-01T02:03:11.482Z",
       "source": { "baseUrl": "...", "sonarProjectKey": "..." },
       "payload": { "...tool-shaped raw data..." }
     }
     ```
   - sends an SQS message (`tool`, `project_id`, `project_name`, `repo_url`,
     `run_date`, `s3_key`, `batch_key`) to the shared ingest queue. `tool` is
     a top-level field because the SQS event-source `FilterCriteria` in
     `template.yaml` (`{"body":{"tool":["<tool>"]}}`) uses it to route each
     message to the one normalize Lambda that owns that tool.
2. **Normalize** (`src/normalize/run.js`, shared by all five
   `src/handlers/normalize-<tool>.js` wrappers): consumes the SQS message,
   fetches the envelope back from S3, runs the tool's parser
   (`src/parsers/<tool>.js`) to get `{ metrics, findings }`, and upserts them
   into RDS MySQL (schema in `db/migrations/001_init.sql`).

Deterministic keys (`src/lib/ids.js`) make every step of this replay-safe:
`s3RawKey(tool, project_id, run_date)` and `batchKey(tool, project_id,
run_date)` are pure functions of the same three inputs used both when
ingest writes the envelope and when normalize re-derives the key to read it
back, so retries and re-runs land on the same S3 object and the same
`ingestion_batches` row instead of creating duplicates.

## D1 -- tool secret `projects` contract

Each tool's Secrets Manager secret (`TOOL_SECRET_ARN` env var on that tool's
ingest Lambda) is a flat JSON object carrying tool-level credentials plus a
`projects` array — one entry per project to ingest for that tool. An ingest
run is treated as "not configured yet" (skips gracefully, does not throw)
whenever `projects` is missing/empty, or when any placeholder field is still
the literal string `REPLACE_ME` (see `isConfigured()` in
`src/ingest/apiPull.js`, reused by `src/ingest/sftpPull.js`). This lets the
pipeline deploy and run its first nightly execution cleanly before an
operator has filled in real tool credentials.

**SonarQube** (API pull) example, once configured:
```json
{
  "baseUrl": "https://sonarqube.example.com",
  "token": "squ_abc123...",
  "projects": [
    { "project_id": "checkout-svc", "sonarProjectKey": "checkout-svc-key", "name": "Checkout Service", "repo_url": "https://gitlab.example.com/svc/checkout" }
  ]
}
```

**GitLab** (API pull) example:
```json
{
  "baseUrl": "https://gitlab.example.com",
  "token": "glpat-abc123...",
  "projects": [
    { "project_id": "checkout-svc", "gitlabProjectId": 4821 }
  ]
}
```
(GitLab's live API response supplies the display name and repo URL, so
`project_name`/`repo_url` in the secret are optional and are overridden by
`glProject.name` / `glProject.web_url` when present.)

**Fortify / Trivy / Tricentis** (SFTP pull) example:
```json
{
  "host": "sftp.example.com",
  "port": 22,
  "username": "quality-dashboard",
  "privateKey": "-----BEGIN OPENSSH PRIVATE KEY-----\n...\n-----END OPENSSH PRIVATE KEY-----",
  "passphrase": "",
  "projects": [
    { "project_id": "payments-api", "name": "Payments API", "repo_url": "https://gitlab.example.com/svc/payments-api", "remotePath": "/exports/payments-api/latest.json" }
  ]
}
```

Before the first real run, an operator must replace every `REPLACE_ME`
placeholder value (base URL, token, host, private key, etc.) that the
secret was seeded with, and fill in the `projects` array for each project
that tool should ingest.

## D3 -- assumed input format per tool, and the XML extension point

The pinned dependency set (`src/package.json`) has no XML parser, so the
three SFTP-pull tools are assumed to drop **JSON**, not their tools' native
XML export formats:

| Tool | Assumed drop shape |
|------|--------------------|
| Fortify SSC | `{ "data": [ { "issueInstanceId", "issueName", "friority", "primaryTag", "audited", "suppressed", "removed", ... } ] }` (an SSC REST-API-shaped issues list, not FVDL XML) |
| Trivy | Trivy's native JSON scan report: `{ "Results": [ { "Target", "Vulnerabilities": [ { "VulnerabilityID", "PkgName", "Severity", "Title", "FixedVersion" } ] } ] }` — this one already matches Trivy's real `--format json` output |
| Tricentis Tosca | `{ "testCases": [ { "id", "name", "status", "durationSeconds" } ] }` (a flattened execution-list shape, not Tosca's native XML/JUnit export) |

If a real deployment lands FVDL (Fortify) or JUnit/Tosca XML instead of
JSON, the extension point is `src/ingest/sftpPull.js`: swap the
`JSON.parse(buf.toString('utf8'))` line for an XML-to-object conversion
(e.g. the `fast-xml-parser` package) before handing the parsed object to
`publishBatch` as `payload`. Nothing downstream needs to change — the
envelope and normalize layers are format-agnostic once `payload` is a plain
object — but `fast-xml-parser` would need to be added as a new dependency
in `src/package.json` at that point, and this build deliberately does not
add it since no real tool feed has proven it necessary yet.

## D5 -- metric_type vocabulary

`metrics.metric_type` has no `tool` column (see
`db/migrations/001_init.sql`), so every name below is globally unique across
all five parsers. Names are scan-class-prefixed (`sast_`, `container_`,
`gitlab_`) only where more than one tool could plausibly emit the same
concept; metrics only one tool emits keep a bare name.

| metric_type | unit | Emitted by | Notes |
|---|---|---|---|
| `coverage_pct` | percent | SonarQube | from measure `coverage` |
| `duplication_pct` | percent | SonarQube | from measure `duplicated_lines_density` |
| `bugs_count` | count | SonarQube | from measure `bugs` |
| `code_smells_count` | count | SonarQube | from measure `code_smells` |
| `tech_debt_minutes` | minutes | SonarQube | from measure `sqale_index` |
| `open_issues_count` | count | SonarQube | derived; always emitted, including `0` |
| `open_mrs` | count | GitLab | count of open merge requests |
| `pipeline_success_rate_pct` | percent | GitLab | omitted when there are 0 pipelines |
| `pipeline_failed_count` | count | GitLab | always emitted, including `0` |
| `gitlab_vulnerabilities_critical` | count | GitLab | |
| `gitlab_vulnerabilities_high` | count | GitLab | |
| `gitlab_open_vulnerabilities` | count | GitLab | findings with state `open`/`confirmed` |
| `sast_vulnerabilities_critical` | count | Fortify | active (non-resolved, non-false-positive) findings only |
| `sast_vulnerabilities_high` | count | Fortify | |
| `sast_vulnerabilities_medium` | count | Fortify | |
| `sast_vulnerabilities_low` | count | Fortify | |
| `sast_open_vulnerabilities` | count | Fortify | total active findings |
| `sast_audited_pct` | percent | Fortify | omitted when there are 0 issues in the raw payload |
| `container_vulnerabilities_critical` | count | Trivy | |
| `container_vulnerabilities_high` | count | Trivy | |
| `container_vulnerabilities_medium` | count | Trivy | |
| `container_vulnerabilities_low` | count | Trivy | |
| `container_open_vulnerabilities` | count | Trivy | Trivy is stateless, so every finding is `status: open` on every run |
| `container_fixable_vulnerabilities` | count | Trivy | vulnerabilities with a non-empty `FixedVersion` |
| `tests_total` | count | Tricentis | |
| `tests_passed` | count | Tricentis | |
| `tests_failed` | count | Tricentis | |
| `tests_skipped` | count | Tricentis | `Skipped` + `Blocked` test cases |
| `test_duration_seconds` | seconds | Tricentis | sum of all test case durations |
| `test_pass_rate_pct` | percent | Tricentis | omitted when there are 0 test cases |

Percent/rate metrics (`*_pct`) are **omitted entirely** — not written as `0`
or `NaN` — whenever their denominator is 0 (see `pct()` in
`src/parsers/common.js`). Plain counts are always written, including `0`,
so a project that currently has zero bugs still gets a `bugs_count = 0` row
rather than a silently-missing metric.

## D6 -- idempotency (never skip a replay)

Every write normalize performs is an upsert, keyed so that re-running the
exact same envelope (a retried SQS message, a re-run nightly batch, a
manual replay) never creates a duplicate row and never throws:

- `projects` / `metrics` / `ingestion_batches`: `INSERT ... ON DUPLICATE KEY
  UPDATE` on their natural unique key (`project_id`; `(project_id, tool,
  run_date, metric_type)`; `batch_key`, respectively) — see
  `src/repo/projects.js`, `src/repo/metrics.js`, `src/repo/batches.js`.
- `findings`: upserted by a **deterministic** `finding_id` = SHA-256 of
  `tool`, `project_id`, and the parser-computed `external_finding_id`
  (`src/lib/ids.js`'s `findingId()`), so the same underlying issue always
  maps to the same row across tools' differently-shaped raw IDs.
- `finding_lifecycle_events`: append-only, but guarded so a replay of the
  identical run never appends a second event for the same finding —
  `src/repo/findings.js` short-circuits when `existing.last_run_date ===
  run_date`.

## D7 -- batch-status transition sequence

`src/normalize/run.js` (`normalizeMessage`) updates `ingestion_batches` in
three separate, deliberately-ordered database calls rather than one big
transaction, so that a status update is never itself rolled back by a
later failure:

1. **`withConnection` (autocommitted), first, before touching S3:**
   upserts the `projects` row and the `ingestion_batches` row (status
   `'ingested'`), using only fields already present on the SQS message.
   Running this *before* the S3 envelope fetch means a batch row always
   exists to be marked failed if literally anything after this point throws
   — including the S3 `GetObject` call itself.
2. **`withTransaction`:** fetches the S3 envelope, parses it, ensures an
   open release exists, upserts every metric and finding, then marks the
   batch `'normalized'` — all inside one transaction, so a failure partway
   through never leaves partial metrics/findings committed.
3. **`catch` block, a separate `withConnection`:** if anything in step 2
   threw, marks the batch `'failed'` with `err.message`, then rethrows so
   the SQS-triggered Lambda invocation itself fails and the message is
   retried (every step above is safe to retry per D6).

## Repository layout (ingest/normalize slice)

- `src/ingest/` — `apiPull.js`, `sftpPull.js` (shared skeletons),
  `publishBatch.js` (S3 envelope + SQS publish), `httpJson.js` (fetch
  helper), `sources/<tool>.js` (API-pull tool-specific HTTP calls).
- `src/parsers/<tool>.js` — pure `parse(envelope) -> { metrics, findings }`
  functions, plus `src/parsers/common.js` for shared helpers (`pct`,
  `externalId`, `metric`, `finding`, severity/status assertions).
- `src/normalize/run.js` — the shared normalize Lambda body described above.
- `src/handlers/ingest-*.js`, `src/handlers/normalize-*.js` — thin per-tool
  Lambda entry points that the `template.yaml` functions point at.
- `src/repo/*.js` — one file per table, each exposing the upsert/read
  functions normalize calls.
- `src/lib/` — `ids.js` (deterministic key derivation), `db.js` (MySQL
  connection/transaction helpers), `secrets.js` (cached Secrets Manager
  reads), `runDate.js` (run-date + MySQL datetime formatting).
- `tests/` — fixtures (`tests/fixtures/<tool>.json`), parser tests
  (`tests/parsers/`), handler-level ingest/normalize tests
  (`tests/handlers/`), plus repo/schema/template/ids tests at the top level.

Run the test suite with `npm test` from the repo root.

## Gate evaluation, notifications, and the dashboard API

This section documents the other half of the pipeline: nightly gate
evaluation, breach notifications, and the eight-endpoint read/write REST
API the frontend and CI/CD pipelines call.

### `gate-eval` (nightly, Step Functions Task)

`src/handlers/gate-eval.js` runs once per night after the ingest/normalize
branches complete. For every project (sequentially — the RDS connection
pool is capped at `connectionLimit: 2`, so handlers never `Promise.all`
DB calls on one connection):

1. Ensures an open release exists (`ensureOpenRelease`).
2. Loads that project's current thresholds (`getCurrentThresholds`, the
   append-only "latest version per metric_type" view — see OED-03 below)
   and its latest metric value per `metric_type` (release-agnostic, since
   `metrics.release_id` is nullable).
3. Evaluates the gate (`src/lib/gate.js#evaluateGate`) and writes one
   `gate_results` row for `(release_id, run_date)`.
4. If the result is `fail`, publishes one SNS message to the shared
   `AlertsTopic`.

**Gate status semantics** (`evaluateGate`): `pass` when every configured
threshold's latest metric passes; `fail` when at least one configured
threshold's metric fails (fail always wins, even if other metrics are
`unknown`); `unknown` when there are no thresholds configured for the
project, or when a configured threshold has no matching metric at all.

**SNS breach message shape** (`publishBreach`), published with
`TopicArn: ALERTS_TOPIC_ARN`:
```json
{
  "type": "gate_breach",
  "project_id": "checkout-svc",
  "project_name": "Checkout Service",
  "release_id": "rel-...",
  "run_date": "2026-09-01",
  "status": "fail",
  "failed_metrics": [{ "metric_type": "coverage_pct", "operator": "gte", "threshold_value": 80, "value": 62, "tool": "sonarqube", "run_date": "2026-09-01" }],
  "dashboard_url": "https://.../projects/checkout-svc"
}
```
with `MessageAttributes: { project_id: { DataType: "String", StringValue: "<project_id>" } }`
so that (a) `notify-slack` fans out to Slack for every breach regardless of
project, and (b) per-user email subscriptions (below) only receive breaches
for the one project they subscribed to.

One project failing to evaluate never blocks the others — each project's
work runs in its own `try/catch` — but the overall `handler()` invocation
still rejects if any project errored, so Step Functions/CloudWatch surfaces
the failure instead of silently swallowing it.

### `notify-slack` (SNS-triggered)

`src/handlers/notify-slack.js` fires for **every** message published to
`AlertsTopic` (no `FilterPolicy` — unlike the per-user subscriptions
below) and posts one plain-text message per SNS record to the Slack
incoming-webhook URL stored in `SLACK_SECRET_ARN` (`{ "webhookUrl": "..." }`).
If the webhook is still the seeded `REPLACE_ME` placeholder, delivery is
skipped (not an error), matching the "not configured yet" pattern used for
the ingest tool secrets.

### Thresholds are append-only (OED-03)

`PUT /projects/{id}/thresholds` (`src/handlers/api-thresholds.js`) never
updates a `thresholds` row in place — every call **inserts a new version**
(`insertThresholdVersion`); "current" is always the row with the latest
`updated_at`/`threshold_id` per `(project_id, metric_type)`. This keeps a
full audit trail of every threshold change instead of losing history on
edit. Only members of the `ReleaseManager` or `QALead` Cognito groups
(`REQUIRED_GROUPS` env var, comma-separated, defaults to
`ReleaseManager,QALead`) may call this route; the group check runs before
any request-body validation or project lookup, so an unauthorized caller
gets a `403` regardless of whether the rest of the request would have been
valid. Every successful call also writes a `user_actions` audit row
(`action_type: 'threshold_update'`, `target_ref: 'project:<id>:<metric_type>'`,
`detail: { previous, next }`).

### Notification subscriptions (self-service, per-project, per-user)

`POST /notifications/subscriptions` (`src/handlers/api-notifications.js`)
lets a signed-in user subscribe their own email address to gate-breach
alerts for one project. It calls SNS `Subscribe` on the shared
`AlertsTopic` with an email-protocol endpoint and a per-subscription
`FilterPolicy`:
```json
{ "FilterPolicy": "{\"project_id\":[\"checkout-svc\"]}", "FilterPolicyScope": "MessageAttributes" }
```
so that subscriber only receives breach messages whose `project_id`
message attribute matches — the shared-topic-plus-per-subscriber-filter
design referenced above, rather than one SNS topic per project. A caller
may only subscribe their own Cognito `email` claim (an explicit
`email` in the request body is accepted only if it matches that claim;
any other address is rejected with `403`) — there is no way to subscribe
someone else's address through this API.

### The eight endpoints (API Gateway + Cognito authorizer, except gate-check)

| Method & path | Handler | Auth | Notes |
|---|---|---|---|
| `GET /projects` | `api-projects.js` | Cognito | List, each with `status` = latest gate result for its open release, or `unknown` |
| `GET /projects/{id}/dashboard` | `api-projects.js` | Cognito | Project + open release + gate + metrics-vs-thresholds + open findings by severity |
| `GET /portfolio/summary` | `api-portfolio.js` | Cognito | Cross-project rollup, sorted by a simple risk score, truncated to `?top=` (1-100, default 20) |
| `GET /findings` | `api-findings.js` | Cognito | Filterable/paginated finding list |
| `GET /releases/{id}/gate-status` | `api-releases.js` | Cognito | Human/dashboard-facing gate status for one release |
| `GET /releases/{id}/gate-check` | `api-releases.js` | **API key only** (`Authorizer: NONE`, `ApiKeyRequired: true`) | CI/CD-facing gate-check; deliberately never reads Cognito claims |
| `PUT /projects/{id}/thresholds` | `api-thresholds.js` | Cognito, `ReleaseManager`/`QALead` only | Append-only threshold version write (see OED-03 above) |
| `POST /notifications/subscriptions` | `api-notifications.js` | Cognito | Self-service SNS email subscription (see above) |

All eight share one request-handling shell, `src/lib/apiHandler.js`
(`createApiHandler`): resolves `${httpMethod} ${resource}` to a route,
parses/validates the JSON body, runs the route inside `withConnection`
(read-only routes) or `withTransaction` (routes declared with `{ handle,
tx: true }` — currently the two write routes above), and maps thrown
`ValidationError`s to `400` and anything else to a logged `500`.

## Frontend

`frontend/` is a React 18 + Vite single-page app: the Cognito-authenticated
dashboard SPA served through the `FrontendBucket`/`CdnDistribution` in
`template.yaml`. It reads portfolio, project, and findings data from
`Api` (the REST API also defined in `template.yaml`) and lets users in the
`ReleaseManager`/`QALead` Cognito groups edit release-gate thresholds.

- **Stack:** React 18, Vite 5, `react-router-dom` v6 (`HashRouter`), plain
  CSS with design tokens. No TypeScript, no CSS framework, no chart
  library, no AWS SDK in the browser bundle — Cognito's sign-up/sign-in
  calls are plain unauthenticated `fetch` requests (see
  `frontend/src/auth/cognito.js`).
- **Build-time config (`VITE_`-prefixed env vars, read via
  `import.meta.env`):**
  - `VITE_API_URL` — stack output `ApiUrl`, no trailing slash
  - `VITE_USER_POOL_ID` — stack output `UserPoolId`
  - `VITE_USER_POOL_CLIENT_ID` — stack output `UserPoolClientId`
  - `VITE_REGION` — fixed at `ap-southeast-1`
  - Copy `frontend/.env.example` to `frontend/.env.production` (generated
    by `./deploy.sh` from the stack outputs) or `frontend/.env.local` (for
    local dev) and fill these in; `frontend/.env.production` and any
    `.env*.local` file are git-ignored.
- **Build output contract:** `npm run build --prefix frontend` (or the root
  `npm run build:frontend`) produces `frontend/dist/` (`index.html` +
  `assets/*`), ready to sync to the `FrontendBucket` and invalidate through
  CloudFront. `vite.config.js` sets `base: './'` so the built assets resolve
  correctly regardless of the path they're served from.
- **Routing:** `HashRouter` — every app URL looks like
  `https://<cloudfront-domain>/#/projects/<id>`. This needs no CloudFront/S3
  rewrite rule beyond the existing 403/404→`/index.html` custom error
  responses, since a hash fragment never leaves the browser.
- **Sign-up / sign-in:** native Cognito `USER_PASSWORD_AUTH` — email +
  password sign-up, a 6-digit email confirmation code, then sign-in. No
  password-reset flow. A newly self-signed-up user starts in **no Cognito
  group** (`Viewer`-level access only); to demo threshold editing, add that
  user to the `ReleaseManager` or `QALead` group from the Cognito console
  (User pools → your pool → Users → select user → Add to group) — this
  project seeds no demo account, per the platform contract.
- **Design tokens:** every colour/spacing/radius/shadow/font value lives
  once in `frontend/src/styles/tokens.css`; see `frontend/README.md` for
  the full restated token table (spacing scale, neutrals, accent, gate
  status colours, severity colours). Severity and gate status are always
  paired with a text label, never colour alone.
- **Tests:** `npm run test:frontend` (Vitest) covers the pure-function
  modules — JWT decoding/claims helpers, the threshold-edit permission
  check, and the API client's query-building/response-normalising helpers.
  UI correctness is verified by browser click-through against the deployed
  stack rather than component/DOM tests, since the API Lambda handlers'
  exact response shapes were still being built out concurrently with this
  frontend.

### Known contract gaps (frontend)

1. `spec/requirements.md` 6.1 and `spec/design.md` describe corporate OIDC
   federation via Cognito; `template.yaml` provisions no identity provider,
   only a native `USER_PASSWORD_AUTH` client. The frontend implements
   native self-signup/sign-in instead, per `CLAUDE.md`'s Auth section,
   which supersedes the spec here.
2. Notification subscription body shape differs between `spec/design.md`
   (`{project_id, channel, target}`) and the task contract
   (`{project_id, email}`); the frontend sends the superset of both.
3. `/findings` pagination and the exact field names inside
   `/portfolio/summary` / `/projects/{id}/dashboard` aren't pinned by any
   spec/schema file; the API client reads every field defensively
   (`normaliseList()`/`pickFirst()` in `frontend/src/api/client.js`).
4. API Gateway's `DEFAULT_4XX` gateway responses have no CORS headers in
   `template.yaml`, so a Cognito-authorizer rejection can surface in the
   browser as an opaque network error rather than a readable 401; the
   frontend mitigates this with proactive token refresh but the underlying
   gateway-response gap is outside this frontend task's scope.

See `frontend/README.md` for how to run the SPA locally and the full design
token table.

## Deployment

`./deploy.sh` and `./destroy.sh` at the repo root are the only two entry
points the platform build system invokes; both are idempotent and exit
non-zero on failure.

**`./deploy.sh`**, in order:
1. Creates the `app-79dad50c-0e543650-artifacts` S3 bucket if it doesn't
   already exist (used as `sam deploy`'s `--s3-bucket`; this bucket is not a
   CloudFormation resource, so it survives across stack updates).
2. `npm install` + `npm test` (backend/template/schema suite, 298 tests).
3. `sam build` + `sam deploy --stack-name app-79dad50c-0e543650-quality-dashboard
   --capabilities CAPABILITY_NAMED_IAM`. Every CFN parameter
   (`NamePrefix`, `PermissionsBoundaryArn`, `VpcId`, `PublicSubnetIds`) has a
   default matching the platform contract, so no `--parameter-overrides` is
   needed.
4. Reads the stack's `Outputs` and runs `scripts/migrate.js` against the
   RDS instance (`DB_HOST`/`DB_SECRET_ARN` from `DbEndpoint`/`DbSecretArn`).
   `migrate.js` applies `db/migrations/*.sql` in filename order, tracking
   applied versions in `schema_migrations` so re-running `deploy.sh` is a
   no-op here too.
5. Writes `frontend/.env.production` from the `ApiUrl`/`UserPoolId`/
   `UserPoolClientId` outputs (the contract `frontend/.env.example`
   documents), then `npm --prefix frontend install`, `npm run test:frontend`,
   `npm run build:frontend`.
6. Syncs `frontend/dist` to the `FrontendBucketName` bucket and invalidates
   the CloudFront distribution (`CdnDistributionId` output — added to
   `Outputs` specifically so a redeploy's changed frontend assets aren't
   served stale from cache; this closes gap #5 from the previous revision of
   this section).
7. Writes `outputs.json` at the repo root: every stack output verbatim, plus
   `app_url` (mirroring `AppUrl`, the CloudFront domain).

**`./destroy.sh`** reverses this: empties and looks up `FrontendBucketName`/
`DataLakeBucketName` from the still-live stack, deletes the stack and waits
for `DELETE_COMPLETE`, then force-deletes (`--force-delete-without-recovery`)
every Secrets Manager secret under the `app-79dad50c-0e543650-` prefix —
CloudFormation's default is a 30-day soft-delete on `AWS::SecretsManager::Secret`,
which would otherwise block a future `deploy.sh` from recreating a
same-named secret — and finally empties and deletes the artifacts bucket.
